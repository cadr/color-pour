# Color Pour

A puzzle generator and solver for a physical color-sorting block puzzle. Design solvable puzzles for your DIY plastic rack (slots with colored blocks), generate them at Easy/Medium/Hard/Expert difficulty, build them physically from a setup list, and step through the solution on-screen with hints.

## Quick Start

1. **Open the app**: Load `index.html` directly in a browser (`file://` URL works — no build step).
   - Or serve locally: `python3 -m http.server` then visit `http://localhost:8000`.

2. **Workflow**:
   - **Setup kit**: Enter just two settings — number of colors (N) and slot height (H, blocks per slot) — plus a name/color for each of the N colors. Everything else about the starting layout is derived automatically (see Rules below).
   - **Save** the kit to browser storage with the Setup panel's "Save kit setup" button; or **Reset kit** to restore the default setup and clear the saved state.
   - **Pick difficulty**: Easy, Medium, Hard, or Expert.
   - **Generate**: Creates a random solvable puzzle; displayed as a numbered diagram showing the initial setup.
   - **Build physically**: Follow the setup list (e.g., "Slot 1 (bottom→top): Red, Blue, Blue, Green") to arrange blocks in your physical rack.
   - **Play on-screen** (optional): Click slots to pour; undo/reset to try yourself. Use "Hint" to see the next move from the current state, or "Show solution" to step through the optimal/near-optimal solution.
   - **Copy link**: Puzzle is encoded in the URL hash; share or bookmark it.
   - **Print**: Print-friendly CSS for the setup diagram and list.
   - **Printable set**: Under "Printable set", choose how many puzzles (1–60) and click **Generate set** to make that many random puzzles at the selected difficulty, then **Print set**. Puzzles print in color, 6 per legal-size page (2 × 3 cut-apart cards), with an optional answer key on the following page(s). In the print dialog pick **Legal** paper and enable **Background graphics** so the block colors print. A typed seed makes the set reproducible (puzzle *k* uses seed `<seed>-k`).

## Rules

**Setup** (matches the physical kit): you only ever pick two settings — the number of distinct colors **N** and the slot height **H** (blocks per slot). Everything else about the starting layout is fixed, not configurable:
- **Slots** = **N + 2**, always (derived).
- **Exactly 2 slots start empty**; the other **N** slots each start **completely full** (H blocks).
- So every color appears **exactly H times** total — there's no per-color block count, no user-chosen slot count, and no user-chosen empty-slot count.

**Classic mode** (default, matches the common digital versions): Pour as much of the top color group as fits into a destination. A pour is legal if the destination is not full and either empty or has the same color on top.

**Strict mode** (all-or-nothing): The entire top color group must fit in the destination; it's rejected otherwise. Choose this mode in the Setup panel if your physical game requires moving all blocks of a color together.

**Solved state**: A puzzle is solved when every slot is either empty or contains a single color (monochrome), with each color consolidated into exactly one slot (since every color has exactly H blocks, i.e. exactly one slot's worth).

## How Generation & Difficulty Work

Puzzles are generated by:
1. Shuffling all `N × H` blocks (seeded PRNG) into one pile and dealing them into the `N` full slots, leaving the other 2 empty — the only strategy that can preserve the fixed "2 empty / N completely full" setup (an "un-pour" scramble of a solved layout would necessarily leave some slots partially filled, which the real kit can't represent).
2. Verifying solvability with an A* solver (not every random deal is solvable, though empirically most are, since two empty slots give plenty of room to maneuver) and computing difficulty metrics.
3. Rejecting layouts with excessive same-color runs at harder difficulties (no pre-sorted slot at Medium+).
4. Scoring by solution length and solver search effort (nodes); selecting the candidate best matching the difficulty band within the time budget.
5. Relaxing the quality gate and retrying more deals if generation stalls.

**Difficulty levers**:
- **Easy**: Shorter solutions, tolerates long same-color runs and even a pre-sorted slot (around 9 moves).
- **Medium**: Moderate complexity, no pre-sorted slots (around 16 moves).
- **Hard**: Longer solutions, short same-color runs (around 24 moves).
- **Expert**: Longest solutions, shortest same-color runs (around 26 moves).

**Performance** (default kit: 8 colors, height 4 → 10 slots):
| Difficulty | Avg Moves | Avg Solver Time | Notes |
|---|---|---|---|
| Easy | ~9 | ~15ms | Often solves instantly |
| Medium | ~16 | ~0.5s | Rapid |
| Hard | ~24 | ~0.4s | Slower but acceptable |
| Expert | ~26 | ~0.1s | Fast pruning of search space |

Larger kits (e.g., 12 colors, height 4 → 14 slots) take longer: Easy ~15 moves, Medium ~24, Hard ~33, Expert ~42, all within ~2.5s.

The displayed solution is **optimal** (shortest path) when the bounded optimal A* search finishes; otherwise, it's a good-but-not-necessarily-shortest one (**optimal-ish**).

## Project Layout

- `index.html` — UI shell; loads engine and app via classic `<script>` tags (no modules, no build).
- `src/engine.js` — Pure game logic (UMD): rules, pouring, solving (A* with heuristic), generation, difficulty scoring, encoding/decoding puzzles.
- `src/app.js` — UI logic: setup panel, generation, puzzle display, play mode (click to pour), solution viewer, persistence (localStorage), printing.
- `src/styles.css` — Responsive design (light/dark mode via `prefers-color-scheme`), mobile-friendly.
- `test/` — Unit and fuzz tests (Node 22 built-in runner).
  - `pour.test.js` — Rules, pouring, legal moves.
  - `isSolved.test.js` — Solved state definition, validation, canonical keys.
  - `solve.test.js` — A* solver, replay, optimality.
  - `fuzz.test.js` — Randomized tests with an independent reference implementation and BFS oracle; validates canPour, isSolved, solve.
  - `generate.test.js` — Puzzle generation, determinism, difficulty ordering, scoring, encoding.
  - `e2e/browser.e2e.js` — Headless Chrome integration test (click setup, generate, play, hint, solution).

## Testing

- **Unit + fuzz tests**: `npm test` runs all `test/*.test.js` files with Node's built-in test runner (Node 22+). Tests include:
  - Pour rules (classic vs. strict) and move legality.
  - Solved-state definition (each color consolidated into exactly one slot).
  - A* solver correctness, replay, and optimality against a BFS oracle.
  - 4 fuzz suites comparing against an independent reference impl. (~30s total).
  - Puzzle generation validity, determinism, and difficulty ordering.
  - The setup invariant: slots = colors + 2, exactly 2 slots start empty, every other slot starts completely full at height H, and each color appears exactly H times.
  - Encoding/decoding round-trips.
  - Quality gates (no pre-sorted slots at Medium+, short same-color runs for hard/expert).

- **End-to-end tests**: `npm run test:e2e` launches headless Chrome via the Chrome DevTools Protocol (zero npm deps). Tests:
  - No console errors on load; unique color labels (e.g. Purple "Pu" vs Pink "Pi").
  - Kit setup (number of colors, slot height) persists across reload (localStorage); invalid configs show a clear error.
  - Blocks render resting at the bottom of each slot in the correct order.
  - Puzzle generation and display at all four difficulties, including the slots/empty-slots/full-slots setup invariant.
  - Play mode (pour, undo, reset, win detection).
  - Hint computation from the current play state.
  - Solution viewer (step through moves).
  - URL hash encoding and reload.
  - Printable set: 6 cards per page, answer key, seeded reproducibility, and a Print-to-PDF check that the set comes out as legal-size pages.

  Override Chrome path with `CHROME_PATH=/path/to/chrome npm run test:e2e` if not auto-detected.

## Known Limitations & Next Steps

- **Difficulty tuning**: On-screen difficulty is currently judged by solver solution length and search effort, not human-perceived difficulty. Tune by playing real puzzles and adjusting quality gates in the generator.

- **Generation latency**: Large kits (12+ colors) can take 1–2.5 seconds and block the main thread. **Future**: Move generation to a Web Worker.

- **Pour rule wording**: Some physical rule sets require moving all blocks of a color at once. Classic (default) pours as much of the top color group as fits, like the common digital versions; switch to Strict in the kit panel if your physical rules require the whole group to move at once.

- **Test timing**: Assertions on solver timing may be flaky on slower machines; consider loosening bounds for CI.

- **Hints**: Use the fast greedy solver (default), so hints may not be the shortest path. "Show solution" is usually shorter (optimal when the bounded optimal search finishes).

- **Possible features**:
  - Saved puzzle library or daily puzzle rotation.
  - Printable cut-out labels for the physical rack.
  - Undo in solution viewer synced with play mode.
  - PWA/offline install.
  - Mapping to the physical rack's actual spatial layout (not just slot numbers).
